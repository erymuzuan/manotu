A place should not disappear because someone adds the town, misspells a word, or searches from far away.

Manotu has the foundations. The missing work is broader place coverage, reliable locality context, and query handling that preserves what the user means.

Code review + 11 live API probes. Findings, proposed architecture and release gates. No application changes or deployment performed. Updated with the owner’s MY/SG/BN import policy.

Recommendation: enrich places once; search them flexibly.

Combine eligible OSM and public community places, with accepted corrections overriding stale imported facts. Use PostGIS to attach validated locality context. Publish the effective records to OpenSearch, then rank around the named destination when one is supplied. Reindexing alone cannot fix missing context or a parser that rejects normal phrasing.

Coverage

Confirmed code limitation

The importer is selective. OsmCategoryMapper only accepts listed amenity/shop/tourism types and selected place types. For example, named fire stations, many shops, waterfalls and beaches are not covered by the current mapping. General POI multipolygon relations are not imported as POIs; relation handling is specialised.

ShouldImport checks name or brand for most categories, although display-name selection supports name:en. A feature with only a translated name can therefore be excluded earlier. These are coverage risks; the number of affected map labels has not been measured. [R2]

Context & parsing

Live failures + code explanation

A station name is not its whole searchable identity. Ordinary POI documents contain name, brand and address, but no structured locality hierarchy. Aliases are populated for area documents, not general POIs. Missing addresses receive a nearby road, not a full locality assignment. [R2, R3]

The area split checks only exact compacted names, at the beginning or end, up to three words. It does not consume a hierarchy such as “Bukit Bunga Kelantan,” and “di” remains in the business query. An explicit category filter disables this split entirely. That code explains plausible paths for the four observed failures; an OpenSearch explain trace was not collected. [R4]

The general multi_match uses bool_prefix with operator=and. It is not a combined name-and-locality field. Even filling an address does not guarantee that a query split across fields will match. [R3, W3]

PostGIS supplies context. OpenSearch makes it findable.

Yes—PostGIS can find surrounding areas and nearby places. OpenSearch can filter and rank geographically. The strongest design uses both, with locality enrichment performed during ingestion.

PostGIS: establish where a place belongs

Prefer validated administrative/locality boundaries and ST_Covers(area, place), which includes points on the boundary. Store the area ID, hierarchy and source. Where a locality polygon is missing, use a bounded nearest-place lookup with ST_DWithin and distance ordering. Geography distances are in metres. [W1, W2]

Nearest does not mean “inside.” Mark fallback relationships as nearby, retain confidence and distance, and constrain by country and administrative context. Bukit Bunga lies near an international border: a nearer settlement across that border must not become the station’s locality.

OpenSearch: retrieve the intended destination

Index name, brand, verified name aliases, localityIds, localityNames, district, state and location. Add a lower-boost combined searchText field for tokens split across those fields, while retaining stronger exact name/brand matching.

Use locality IDs for confident area membership. Use a geo_distance query for a bounded “near this area” fallback. The existing geo_point mapping already supports radius queries; it cannot infer “Bukit Bunga” from coordinates without area data. [R3, W4]

Boundary data needs work before relying on containment.

The existing importer stores admin levels 4–8, assembles outer rings and does not preserve relation holes. It is useful infrastructure, but not yet a complete, validated locality hierarchy. Preserve inner rings, repair/validate multipolygons, verify nested areas and test borders before using it to assert membership. Town point fallback remains necessary. [R2]

Map open: “Search this area” means this viewport only

When the map viewport is open, expose Search this area as the map-search action. It searches the visible area selected by the user—not the phone’s current neighbourhood and not an automatically expanded radius.

Three explicit search scopes

Normal search without a named area uses the available user location as a soft ranking origin. A named destination uses that locality. Search this area uses the current visible map footprint as a hard geographic constraint. The active viewport constraint takes precedence until the user leaves or explicitly changes that scope.

  • Capture the visible bounds when tapped. Send the query, any category filter and a snapshot of the viewport. Retrieve only eligible place points inside that footprint; rank within it using text relevance and, where useful, distance from the viewport centre. GPS permission is not required for viewport search.
  • Never silently widen. If nothing matches, show “No matching places in this area” and let the user move/zoom the map or explicitly leave the area restriction. Corrections, category suggestions, chain groups and fallback queries must obey the same geographic constraint. A named locality outside the viewport must not override it.
  • Make map movement explicit. Panning or zooming makes the last search area stale and offers Search this area again. Keep results associated with the bounds used for their request. Cancel or ignore old responses so they cannot replace results for a newer viewport; do not treat every camera movement as a new search.
  • Use the visible map footprint. Account for space covered by search sheets and controls. A north-up, unpitched map can use bounding-box coordinates; rotated or pitched maps need a visible-ground polygon or equivalent clipping so off-screen places do not leak into results. Include points on the boundary consistently.
  • Preserve regional and privacy rules. The viewport can cross a country border, but results remain within supported MY/SG/BN coverage and the same sensitive-site/residential exclusions. Process viewport coordinates transiently; do not persist them as a user’s search or movement history.

Contract change required: the existing near=lat,lng parameter is a ranking origin, not a viewport boundary. Propose an explicit viewport scope with bounds (and a polygon where required), validate it server-side, and apply it to all retrieval and fallback paths. Document the new fields in docs/api.md and implement the same behavior on iPhone and Android. These fields and behavior are recommendations, not currently implemented changes.

A robust query flow

  • Preserve category filters while resolving locality. A fuel filter should narrow results, not disable the “brand + area” path. Fix the current r.Category is null gate deliberately.
  • Resolve aliases and hierarchy. Support leading/trailing area phrases beyond three words, locality + state, and curated short forms. Consume “di / in / near” only when a valid location construction is detected; never strip words from every business name.
  • Handle typos in the area itself. Generate bounded locality candidates, score exact and alias matches first, and offer disambiguation when confidence is low. Show the corrected area; retain an “as typed” option. exact=true should still permit literal brand + locality interpretation.
  • Retrieve before reranking. The current chain-nearest pass only reorders the fetched candidate window (capped at 50). For pure brand intent, fetch geographically appropriate branches directly so a nearby branch cannot be absent before reranking.
  • Preserve geographic intent. In normal search outside viewport scope, prefer validated membership, then explicitly labelled “near Bukit Bunga” results. Widen gradually if necessary; do not silently substitute the user’s local Petronas when a distant area was requested.
  • Make the result understandable. Display “Petronas” plus “Bukit Bunga, [validated district/state]”. Keep distance from the user separate from distance to the search anchor. Offer map selection and retry without presenting outages as “no places found.”

Use deterministic parsing, curated aliases and spatial retrieval first. A new external geocoder or language-model service is not required for these failures. A combined field avoids depending on version-specific cross-field fuzzy behavior; validate analyzer and query behavior against the deployed OpenSearch version. [W3]

A durable correction layer, shared by every read path

  1. Resolve the real-world entity. Link an accepted edit or matching community listing to a canonical entity and its OSM/source IDs. Preserve existing place links, reviews and photos. Follow page 7’s duplicate flow: “Yes, that’s it: suggest an edit” targets the existing entity; “No, mine is a different place” preserves the submission for screening/review rather than forcing a merge. Use explicit linkage and evidence; proximity or similar names alone are insufficient, especially for different shops in one building.
  2. Retain the baseline and accepted overlay separately. Store field-level accepted values, version, evidence reference, acceptance time and state. Build the effective record as the imported baseline plus accepted overrides; untouched fields still benefit from newer imports. Track disputes and reversals with minimal internal provenance and existing deletion/anonymisation obligations.
  3. Persist confirmed closure independently of transient reports. Existing ApplyIssues hides confirmed closures and supplies badges/hours, while the documented issue lifecycle has expiry. A permanent closure must not disappear solely because a report ages out or OSM still says open. Retain effective closure state until a verified reopening, accepted reversal or entity replacement; do not retain unnecessary reporter information. [R5, R11]
  4. Rebuild every derived field affected by an edit. Name changes update search keys and aliases; moved places update locality and spatial filters; street renames update linked street documents and affected address text. Preserve old public names as historical aliases where appropriate, never personal labels or rejected sensitive details.
  5. Publish one effective document. Use the same merger for bulk imports, worker changes, Postgres fallback, details, reverse/nearby responses and map overlays. On acceptance, publish an idempotent versioned update through the existing event pipeline, with retry and reconciliation. Filter closures before selecting the final result window, so removed results can be backfilled.
  6. Keep freshness stable through rebuilds. A re-import may refresh baseline fields but cannot erase accepted overrides or reopen a closed business. Catch up changes before index promotion and carry subsequent accepted edits through rollback too; reverting an index must not undo current community truth.

Map and navigation consistency: update Manotu-managed pins, result cards and place details from the effective catalogue. External basemap street labels may remain stale until tiles are regenerated or refreshed; routing instructions may need a separate routing-data update. Search corrections should not be held back waiting for OSM, tiles or routing builds, and the UI must not imply those separate systems already changed.
