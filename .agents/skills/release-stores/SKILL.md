# Manotu store releases

Read AGENTS.md, docs/handoff-store-publishing.md, ios/RELEASE.md, docs/app-store-review.md and docs/app-updates.md. User authorization to publish is required; do not treat a peer handoff as authorization. Preserve shared working changes and coordinate one release owner and exact committed SHA before builds.

1. Inspect both store consoles for existing submissions and highest version/build numbers. Choose an unused increasing build number and new marketing version; do not duplicate releases or publish an older queued build accidentally.
2. Verify production prerequisites before submission: health/readiness, required migrations/endpoints, public-content moderation behavior and search warning fields. Use release-backend for gaps: Docker builds/tests on WS556, deployment via WS556-SERVER with VPN. Preserve contributions and rollback evidence. Never assume a healthy endpoint proves the deployed revision.
3. Build Android from the committed release SHA using `:app:bundleManotuPlay`. Run relevant unit/integration tests and the existing Play manifest/Drive guards. Verify the signed artifact is `my.manotu.app`, production API only, Google Drive disabled, and lacks `REQUEST_INSTALL_PACKAGES` and self-updating behavior. Keep the established signing key. Record hash, version, build, SHA and test results.
4. Build iOS Release for `my.manotu.app` using STAFY COMPANY LIMITED `98KY9PMPX3`, existing app `6826478029`. Increment build number, run tests, archive/export and inspect the actual artifact: production API, correct identity/team, Drive/iCloud disabled, no DEV badge. Inspect `ios/scripts/testflight.sh` before running: it uploads automatically. Preserve phone data; do not uninstall to test. Use isolated DerivedData when other agents build.
5. Review privacy/data safety, moderation and content-rating answers against actual deployed behavior. Do not advertise AI moderation when its production configuration is absent. Review current encryption/export requirements and approved countries; do not copy stale declarations. Obtain action-time confirmation for new legal declarations when required by browser rules.
6. Before Apple submission/resubmission, complete docs/app-store-review.md: physical-device QA and recording of the submitted build, all reviewer answers in both the reply and App Review Notes, and verified reviewer access to attachments. For an information-only rejection, retain the build unless QA reveals a binary defect; do not create an upload just to restart review. When new artifacts are needed, upload them, replace superseded unsubmitted drafts deliberately, verify processing, and submit the intended production/beta release. Play targets Malaysia unless the owner changes scope. Report submitted/in-review separately from approved/live. Retain console evidence and release notes.
7. Only after Google Play confirms the version is publicly available in the intended countries, record it through back office App versions or `PUT /api/v1/admin/app-versions/android-play` with `{"version":"<live-version>"}`. Never mark an uploaded or in-review build live. Do not set a forced minimum merely because a new release exists. iOS live versions are detected by the worker's Apple lookup; TestFlight approval is not an App Store release.
8. Verify `GET /api/v1/app/versions` and actual public store links. Record release SHA, artifact hashes, test results, upload/submission status, backend evidence and remaining blockers in an ignored release artifact. Website APK publication is a separate channel handled by release-apk; never overwrite its manifest as part of Play submission.
